# Domain: meal-planning

## Purpose

The weekly meal calendar: a plan covering a date range, with one or more entries per day and
meal type, filled in by hand or generated by the AI from the user's profile and history.

## Main Flows

**Read / create** - `GET api/meal-plans` (by range), `POST api/meal-plans`.

**Entries** - `POST api/meal-plans/{planId}/entries`,
`PUT api/meal-plans/{planId}/entries/{entryId}`,
`DELETE api/meal-plans/{planId}/entries/{entryId}`. An entry points at either a `Recipe` or a
`FoodItem` (both nullable) with `Servings` and optional notes.

**Slot rules live on the entity.** `MealPlan.Covers(date)` and
`MealPlan.OccupantsOf(date, mealType, exceptId)` are what the use cases ask before accepting an
entry - a date outside the plan, or a slot already occupied, is refused with a `Failure(...)`
`ProblemDetails` carrying a reason the client can show.

**AI generation is day by day.** `POST api/meal-plans/generate/stream` (SSE) walks the date
range one date at a time: one model call per day, parsed with `MealPlanPrompt.ParseDay`, saved
before the next is asked for. `POST api/meal-plans/generate` (blocking) consumes the same
iterator and discards the narration, so there is only one set of rules about what a half-written
week means. Both clients use the streamed endpoint.

Each day's prompt (`MealPlanPrompt.BuildDay`) carries the profile and targets, the exclusions,
the guidance, the previous period (via `PlannedMealReader`, for "reuse last week's Thursday
breakfast"), the slots **already on the calendar for that date**, and what earlier days of the
same run produced (so day five does not repeat day two's dinner).

Stream events: `progress` (`MealPlanProgressDto` — date, day N of M, `planning|saved|kept|failed`),
`delta` (that day's narration), `part` (`MealPlanDayDto` — the day's saved entries, so the
calendar fills in live), and a final `result` (`MealPlanGenerationResultDto` — the plan plus
`failedDates`, `keptDates`, `stoppedEarly` and a ready-to-show `message`).

Rules worth keeping: the plan row is created lazily on the first day that succeeds (a run that
fails outright leaves nothing behind); an occupied slot is never overwritten, both in the prompt
and again when saving; and the run stops after `MaxConsecutiveFailures` (2) failures in a row,
because that means the provider is down rather than the day being awkward. Plans are marked
`IsAIGenerated`.

## Data and State

`MealPlans` (user, name, `StartDate`/`EndDate` as `date`, `IsAIGenerated`) and
`MealPlanEntries` (`EntryDate`, `MealType`, nullable `RecipeId` / `FoodItemId`, `Servings`,
notes). The grocery list for a range is compiled from these entries - see `domains/grocery.md`.

## Known Gotchas

- The planner used to issue one query per meal; the reads are now batched and no-tracking
  (commit `389a2be`). Do not reintroduce a per-entry query inside a loop.
- A rejected slot must return `Failure(...)`, not a bare string - the mobile client only shows
  `detail` / `title`, which is why rejected slots once said nothing about why.
- `MealPlanPrompt` is shared by the blocking and streaming paths on purpose; adding a
  provider-specific prompt builder would let them drift.
- `ParseDay` also accepts the whole-plan `{"days":[...]}` shape even though `BuildDay` asks for
  `{"meals":[...]}` — a model answering in the shape it knows is still answering, and throwing
  that away would fail a day that had really been planned.
- A generation result is `MealPlanGenerationResultDto`, not a bare `MealPlanDto`. A client that
  reads only `.plan` still works, but it will not tell the user which dates are missing.
- The per-day model call is what makes generation viable on a slow local model: one day fits
  inside a provider timeout where a whole week never did.
- `EntryDate`, `StartDate` and `EndDate` are `DateOnly`, mapped to `date` columns.
